PART 1

The Multi-Tier Log Aggregator

Critical analysis

The snippet has more than three problems, so rather than list twelve at equal weight I've grouped them by what actually happens when you run it, and led with the four that would keep me up at night.

01

The security group is not “permissive”. It is absent.

protocol = "-1" with ports 0–0 means all protocols, all ports, from the entire internet. Not 443, not “the app port and SSH” — everything.

The scenario says this box processes high-volume transaction data. So the exposure isn't “a host gets popped and we rebuild it”; it's an internet-reachable host holding regulated data, which in most contexts is a reportable breach. Fails CIS 4.1/4.2, PCI-DSS 1.2.1 and SOC 2 CC6.1, and GuardDuty flags it within the hour.

This is not a tuning problem — which is why the redesign has zero ingress rules rather than narrower ones.

02

No IAM role, which forces a worse problem

No iam_instance_profile means no AWS identity. The instance still has to write logs somewhere, so either it can't do its job or — far more likely — somebody put static access keys in userdata, an env file, or the AMI.

The missing role doesn't just skip a best practice; it creates active pressure toward the worst available alternative. Combined with flaw 1, an attacker who reaches this host gets credentials that neither expire nor scope.

03

security_groups is the wrong argument, and the way it's wrong is subtle

It's the EC2-Classic argument and takes group names; in a VPC you need vpc_security_group_ids with IDs. In a non-default VPC this fails outright.

The more instructive bug is the second one: it's a hardcoded string, not aws_security_group.allow_all.name. Terraform builds its dependency graph from references, so there is no edge between the instance and the group. Terraform is free to create them in parallel, and on a cold apply it frequently creates the instance first and fails — or silently attaches a stale group of the same name from a previous environment.

It looks like it works, it passes review, and it fails intermittently on fresh applies. That's the worst possible failure schedule.

04

No egress block, which silently breaks the application

AWS gives every new security group a default allow-all egress rule. Terraform's aws_security_group resource is authoritative for its rules and deliberately removes that default when the resource is declared without an egress block.

So the net effect is: the whole internet can reach the log processor, and the log processor can reach nothing. It can't ship to S3, call CloudWatch, or reach a collector. The apply succeeds, the instance boots, the dashboard is green, and no logs arrive.

You get the security posture of a public server with the functionality of an air-gapped one — precisely backwards.

Redesign

The decision that shapes everything else

The snippet describes an instance that receives logs. I deleted that requirement. The rewritten pipeline is pull-based, and every other improvement falls out of that one change.

Three things follow from that single change, and they are the whole redesign:

  • The fleet needs no inbound ports. Not narrower rules — none. You cannot misconfigure an ingress rule that doesn't exist.
  • Processors become stateless and disposable. Losing one costs a shard-lease handover, not data. That makes Spot safe, which pays for most of the multi-AZ redundancy.
  • A bad deploy becomes recoverable. Roll back, reset the checkpoint, reprocess. Without the buffer, a parser bug silently destroys data you can never get back. This is the most valuable property in the design.

An optional internal NLB sits behind enable_direct_ingest for legacy appliances that can only emit syslog over TCP — “how do the old JVM services get in” is the first honest objection to a pull-based design, and I'd rather answer it in code than hand-wave it.

Availability and durability

ASG across every AZ supplied, min_size validated >= 2, instance refresh with checkpoints at 25/50/100% and auto-rollback. A mixed-instances policy keeps an On-Demand floor and bursts on Spot across three Graviton types — defensible specifically because of the pull-based design. A lifecycle hook gives a terminating worker 120 seconds to checkpoint, shrinking the duplicate window to near zero.

Two scaling policies, because they answer different questions:

  • CPU target tracking at 55% — handles the normal daily curve.
  • Step scaling on iterator age — handles falling behind, which CPU will never detect. A fleet blocked on a slow downstream sits at 40% CPU while the backlog grows.

There's also a plan-time precondition that fails if the supplied subnets resolve to fewer than two AZs. “Three subnets, all in eu-west-1a” passes code review every time and only reveals itself during an AZ event.

The alarm I'd keep if I could only have one

no-records-processed, with treat_missing_data = "breaching". Every other alarm fires when something breaks. That one fires when everything goes quiet — which on a log pipeline is the failure that costs you, because you cannot retroactively collect logs you never ingested.

Testing the guardrails

tests/guardrails.tftest.hcl uses Terraform's native test framework with mock_provider, so it runs in seconds with no AWS credentials and belongs in the PR pipeline. Each test asserts one property that, if it regressed, would reintroduce exactly the flaw the redesign exists to fix — plus expect_failures cases proving single-AZ input and min_size = 1 are rejected at plan time.

This is how “we fixed the open security group” becomes “the open security group cannot come back.”

AI verification

I gave the rewritten module to Claude as a hostile reviewer, asking for things that break in production rather than style issues. Three responses below: one I accepted immediately, one I accepted only after checking, and one I pushed back on.

Accepted & fixed The two scaling policies will fight each other

Your target-tracking policy has disable_scale_in = false, so it removes capacity whenever CPU sits below 55%.

Now consider the case your step policy exists for: consumers blocked on a slow downstream. Iterator age climbs, the step policy adds 50% capacity, the new instances block on the same downstream and sit idle. Average CPU stays low — arguably drops, since you've diluted it across more instances. The CPU policy now scales in while the backlog grows. Conflict resolution favours the larger capacity at any instant, so you won't scale to zero, but the cooldowns interleave and you get sustained churn while the backlog goes unaddressed.

I agree completely, and changed the code — disable_scale_in = true on the target-tracking policy.

The bug exists in neither policy alone. Read cpu in isolation: correct. Read backlog in isolation: correct. The defect lives in the interaction under a specific load shape, and it would have presented in production as “the ASG is weird during incidents” — the kind of thing that gets explained away rather than diagnosed.

It also sharpened which signal owns which direction. CPU knows whether we're working hard; only iterator age knows whether we're done. So CPU may scale out, and only the backlog policy may scale in. Cleaner than what I'd written, and I wouldn't have articulated it unprompted.

Accepted after verification The Glue table returns zero rows in Athena

Firehose writes to raw/dt=YYYY-MM-DD/ as configured, but a Glue partition key is only queryable once the partition is registered — and Firehose registers nothing. You need a crawler, MSCK REPAIR TABLE, or partition projection.

I didn't take this on trust, because “your code silently returns nothing” is both serious and easy to assert confidently. I checked it against AWS's own Athena page for this exact Firehose case. It's correct.

Fixed with partition projection rather than a crawler: projection computes the partition list from the query predicate, so there's nothing to register and nothing to fall behind. A crawler costs money and drifts; MSCK REPAIR gets slower every day.

Worth flagging for its failure signature. The apply succeeds, the console looks perfect, objects are visibly landing in S3 — and the people who need the data get an empty result set they'll read as “no matching logs” rather than “the table is broken.”

Pushed back Drop disable_api_termination — it blocks Auto Scaling

Remove it from the launch template; it will block Auto Scaling from terminating instances and break both scale-in and instance refresh.

I checked this one too, and the reasoning as stated is not quite right: EC2 termination protection and ASG instance scale-in protection are distinct mechanisms, and the ASG isn't simply blocked by the former in the way the critique implies.

I removed the setting anyway, for a different reason. Termination protection on an ASG-owned instance is fighting the component whose entire job is terminating instances — scale-in, unhealthy replacement and instance refresh all work by terminating. Even where the behaviour is benign it's semantically confused, and confusion at that layer is how you end up debugging a stalled refresh during an incident.

What I actually wanted was protection against terraform destroy against prod. That belongs at the Terraform and CI layer — plan review, a protected workspace, a pipeline that refuses destroy plans on the prod branch. Right instinct, wrong layer.

Two more it caught that I fixed without argument

  • The ASG used a fixed name with create_before_destroy — the exact duplicate-name deadlock I'd written a warning comment about on the security group twenty lines earlier, and then walked straight into.
  • instance_refresh.triggers listed desired_capacity, which is in ignore_changes. A trigger that can never fire: harmless, but it reads like intent and would mislead the next person.

What I take from the exercise

The valuable findings were all about interactions — two policies, a Firehose prefix and a Glue table, a lifecycle rule and a resource name. Those are exactly the defects that survive human review, because we read resources one at a time. That's a real complement to how I work.

The failure mode runs the other way. The disable_api_termination critique was confidently argued and mechanically wrong; the Glue one was confidently argued and right. They were indistinguishable in tone, and both needed verification against primary sources before I acted. I'd apply the same rule to a very senior human reviewer — but the volume and fluency of the output makes it much easier to skip that step, and the cost of skipping it is a plausible-sounding change to production infrastructure.

Automation & Data Manipulation

#!/bin/bash
grep "Failed login" app.log | grep -oP "Username=\[\K[^\]]+" | sort |
uniq -c | sort -nr | head -n 5

The edge case break

The one-sentence version

Every one of its failure modes produces empty output and exit status 0. To cron, systemd or CI, “the log format changed six weeks ago” is indistinguishable from “no failed logins today.” It doesn't break loudly — it starts lying quietly.

demo_failure_modes.sh reproduces each of these against real fixtures rather than asserting them. Verified output:

The scenario I'd actually bet on: structured logging

The most likely thing to break this isn't load or a weird character. It's a routine, well-intentioned migration to JSON: 

{"timestamp":"2026-09-14T11:00:01Z","event":"Failed login","username":"alice"}

Nothing errors. grep "Failed login" still matches — the phrase is right there. But Username=[...] no longer exists, so the second grep yields nothing, and the pipeline prints nothing and exits 0.

The security dashboard reads zero failed logins. Forever. Nobody investigates zero. And this is worse than a crash in a specific way: a crash is fixed in an hour; this is discovered during an incident review six months later, when someone asks why there's no record of the credential-stuffing campaign.

The rest, by category

Silent tooling failures. grep -P needs PCRE compiled in. On Alpine/BusyBox, on macOS with BSD grep, and on minimal container images, it isn't there. Error to stderr, empty output, exit 0. Moving this into a slim image breaks it without a single line changing.

Exit codes that mean the opposite of what you'd think. With a missing app.log, grep exits 2 but the pipeline's status is head's, which is 0 — cron records a successful run over a file that doesn't exist. Harden it with set -o pipefail and you get the reverse: head closes the pipe, sort dies on SIGPIPE, and a completely successful run returns 141. Verified:

verified locally
$ ( set -o pipefail; seq 1 200000 | sort -nr | head -n 1 >/dev/null; echo $? )
141

So the unhardened version fails open and the hardened version fails closed at random. Neither is monitorable.

Log rotation. It reads one static path. With create, app.log is a brand-new empty file, so counts reset at rotation time and app.log.1/.2.gz are invisible. With copytruncate, there's a window where the file is copied and truncated mid-read, producing a partial result with no indication. Either way the numbers reset on a schedule nobody correlates with the graph.

Volume. sort on a multi-GB extraction spills to /tmp — partial output and exit 0 on a small /tmp, or you fill the disk and take the application down with the monitoring tool. It's O(n log n) time and O(n) disk to answer a question that's O(n) time and O(distinct) memory with a hash map. And every run rescans from byte zero, so cost grows with file age and every event is recounted.

Correctness. Case-sensitivity misses failed login and FAILED LOGIN — 1 of 3 real events in the demo. [^\]]+ trusts a delimiter an attacker controls, so a user registering as eve] Username=[admin makes the script report failures against admin that never happened: an attacker can steer your security dashboard. And sort -nr | head breaks ties by whatever order the previous sort produced, so two runs over identical data can disagree about who's fifth.

The analytical flaw underneath all of it

Even working perfectly, it counts all of history. No time window. So an incident from three months ago permanently dominates the top 5, and the tool reports the same five names every day regardless of what's happening now. Every other issue is a bug; this one is a category error — a historical trivia query wearing the costume of a monitoring tool.

Hanging. Pointed at a FIFO, grep blocks forever — in a cron job, holding whatever lock it holds, with no output and no timeout.

The modern alternative

tools/log_analyzer.py — Python 3.8+, standard library only, with a 40-test suite that passes.

OK

Why stdlib-only. A deliberate constraint, not laziness. A monitoring tool that needs pip install cannot run on the legacy hosts it exists to monitor — the ones with no egress, an old system Python, and a change freeze. It also can't break from a transitive dependency update, and the same file runs identically on a 2015 VM and in a distroless container.

Core design principle

A monitoring tool that can't distinguish “nothing bad happened” from “I am broken” is worse than no monitoring tool, because it manufactures confidence.

Deployment

Same file, two schedulers. systemd for legacy hosts: Type=oneshot with a hard timeout so a slow run can't overlap the next and corrupt the checkpoint; MemoryMax and CPUQuota so the monitor can never cause the incident; ProtectSystem=strict; and RandomizedDelaySec on the timer so the fleet doesn't hit the same downstream at :00 — the same thundering-herd shape that shows up in Part 3. Kubernetes CronJob for the containerised services, with concurrencyPolicy: Forbid and a memory limit sized so the cardinality guard trips before the OOM killer does.

The honest caveat

At Smartology's scale this is the portable fallback, not the destination. The real answer is the Part 1 pipeline: emit structured JSON at source, land it in the lake, and answer “top 5 failed logins in the last 15 minutes” with Athena over indexed Parquet — no host-local parsing at all. Two reasons it still earns its place:

  • Legacy hosts that will never emit to Kinesis. There are always some, and they're usually the ones you most want visibility into.
  • It's an independent check on the pipeline. Comparing its local count against what the lake reports is a genuine end-to-end test of ingestion — performed by something with no shared failure modes with the thing it's checking.
PART 3

Production Escalation

Blue-green cutover completes, the load balancer shifts to green, database CPU immediately hits 100% on a wave of reads, the web tier starts dropping client connections.

First principle

The first decision isn't “what's wrong” — it's shift traffic back to blue. Target 60–90 seconds. Blue is still warm and at full capacity; that is the entire reason we paid for blue-green.

I want to be precise about why, because “just roll back” can sound like avoiding the question. Under this failure the database is saturated, so blue is degrading too — it shares the database. Every minute spent diagnosing is a minute of customer-visible errors, and a saturated database makes diagnosis harder anyway: everything is slow, so everything looks like the cause.

The one check before rolling back, about fifteen seconds: did this release run a schema migration? If green applied one blue's code can't read — a dropped column, a renamed table, a changed type — rolling back trades a performance incident for a correctness incident, and correctness incidents corrupt data. If a migration ran and isn't backward-compatible, I fix forward under a maintenance page. (This is also the argument for expand-contract migrations as policy: it's what keeps the rollback lever safe to pull.)

Capture evidence first — the rollback erases the state that explains the incident. While traffic shifts: a Performance Insights screenshot of load by wait event, a pg_stat_statements snapshot, a pg_stat_activity dump, one thread dump from a green instance, and the ALB access logs for the cutover window. Thirty seconds of capture saves a week of “we never found out what happened.”

What I check first, in order

The goal of the first five minutes is not root cause. It's one question: is the database doing more work, or the same work more slowly? Everything downstream is a different investigation.

Minute 0–1

Is it actually the database?

One CloudWatch dashboard, four metrics side by side:

  • RDS CPUUtilization + DatabaseConnections — confirms the constraint
  • RDS ReadIOPS / ReadThroughput — CPU-bound or IO-bound?
  • ALB TargetResponseTime, HTTPCode_Target_5XX, RejectedConnectionCount — confirms the impact and its shape
  • ASG/ECS instance or task count — did green come up with a different count than blue?

The highest-value thirty seconds in the whole incident: compare DatabaseConnections immediately before and after the cutover. A step change — blue was 200, green is 600 — is a connection-storm signature, and it points at configuration, not code. Every green instance opens a full pool on startup; more instances, a larger max_pool_size, or eager warming multiplies connections without changing a line of logic. On PostgreSQL each connection is a backend process, and past a few hundred you're burning CPU on context switching rather than queries.

If connections are flat and CPU is pinned, it's query work. Different branch.

Minute 1–3

RDS Performance Insights

The tool that answers the question — and the reason it should be enabled on every production database before you need it. Database load by wait event gives the shape immediately:

Minute 3–5

The discriminator

Take the top query and compare calls and mean_exec_time against the pre-deploy baseline.

SELECT
  substring(query, 1, 100)          AS query,
  calls,
  round(mean_exec_time::numeric, 2) AS mean_ms,
  round(total_exec_time::numeric)   AS total_ms,
  rows / GREATEST(calls, 1)         AS rows_per_call
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

Application loop vs database limitation

The discriminator, in one sentence

One query running 50,000 times instead of 50 is an application problem. One query taking 4 seconds instead of 40ms is a database problem. Both present as “database CPU at 100%”. They have almost nothing else in common.

That last row is the cheapest decisive test. Shift 5% of traffic to green. If the database calms proportionally, it's volume — an application loop. If a single query is still slow with almost no load on it, it's the query.

The four causes I'd check by name

In descending order of how often I've seen each cause this exact symptom on a cutover:

01

Green reads from the writer endpoint instead of the reader

Far and away the most common blue-green database incident, and it matches the symptom precisely: “a massive wave of read requests.” The reader endpoint is configured per-environment, and green is a new environment — a copy-pasted config, a missing variable falling back to a default, a Terraform output wired to the wrong attribute, and 100% of reads that used to spread across three replicas land on the primary.

Thirty-second check: writer CPU vs reader CPU. Writer pinned at 100% while readers sit at 5% is conclusive. No further investigation needed.

02

Cold cache → stampede

A fresh ElastiCache cluster, a flushed cache, or release-versioned keys mean every request is a miss and every miss hits the database — and concurrent identical misses all issue the same query.

Check: CacheHits/CacheMisses and Evictions across the cutover. A hit rate that fell off a cliff at the exact cutover timestamp is the answer. This one is nasty because it's self-inflicted by the deployment strategy: blue-green with a per-environment cache guarantees a cold start every release.

03

An N+1 introduced by an ORM change

A removed include, a lazy-loaded association inside a loop, a serializer that now touches a relation. Signature: calls up by orders of magnitude, mean_exec_time flat, rows_per_call = 1.

Check: one APM trace of a single slow request. If the waterfall shows 400 near-identical 2ms queries, the trace is the bug report.

04

A plan regression

The migration added or dropped an index, or statistics went stale on a table that grew, and the planner flipped from index scan to sequential scan. Signature: calls flat, mean_exec_time exploded, waits dominated by IO:DataFileRead.

Check: EXPLAIN (ANALYZE, BUFFERS) against blue's plan. A Seq Scan where blue had an Index Scan is conclusive. Sometimes the fix is just ANALYZE.

Structural fixes — the actual lesson

The interesting question isn't “what broke”, it's why a big-bang cutover seemed acceptable for a change of this kind.

  • Canary, not big bang. 1% → 5% → 25% → 100% with automated rollback on error rate and database CPU. Nearly every failure above is visible at 1% and harmless there. Big-bang is fine for stateless services that share nothing; it's a poor fit the moment blue and green share a database, because the blast radius isn't contained by the deployment strategy at all.
  • RDS Proxy or PgBouncer. Decouples instance count from connection count and removes the connection-storm mode as a class.
  • Query budgets in CI. Assert a checkout issues fewer than N queries. Catches N+1s at PR time, where they're cheap. Highest-leverage item on this list.
  • Cache warming as a deploy step, so the strategy stops manufacturing cold starts.
  • Expand-contract migrations as policy, so the 60-second rollback decision never needs a caveat.
  • Load-test green against production-scale data. Most of these are invisible against 10k rows and obvious against 10M.
PART 4

System Architecture — Orbit

A multi-region e-commerce order and fulfilment platform: event-driven microservices on EKS, polyglot persistence, GitOps delivery with progressive rollout. Drawn at the level where the interesting arguments live — the request path, the consistency boundaries, and the places the design is knowingly imperfect.

What this is, stated plainly

Orbit is a composite reference architecture, not a system I personally built. It's here to make the design discussion concrete, and I'd rather say so up front than have it surface as a surprise under questioning.

The individual pieces are ones I have worked with in production: AWS infrastructure deployed and managed end-to-end with Terraform, CloudWatch and CloudTrail for monitoring and audit, Prometheus and Grafana for dashboards, Route 53 for DNS, Ansible for configuration management across remote servers, and MySQL running inside a Kubernetes environment. I led an infrastructure project at Etihad Airways and worked on the Banque Misr mobile app in production — happy to drop this diagram and walk through either of those instead.

The checkout path

  1. Client request hits CloudFront; cacheable assets never reach the origin.
  2. WAF evaluates, ALB terminates TLS and routes to the BFF.
  3. BFF composes the call and forwards to the order service.
  4. Order and outbox row are written to Aurora in one transaction.
  5. Payment authorises against the external PSP — synchronous, unavoidably.
  6. Inventory reserves stock in Redis against a durable ledger. (Order orchestrates 5 and 6; drawn as a chain for legibility.)
  7. The relay publishes committed outbox rows to EventBridge. This is the async boundary.
  8. EventBridge fans out to per-consumer SQS queues, each with its own DLQ.

The outbox is what makes “order committed” and “event published” atomic without a distributed transaction — the event row commits with the order or not at all.

Limitations

I'd rather present these than be asked for them.

01
Single-region writes

Aurora Global Database gives roughly a one-second RPO, but promotion is operator-initiated and realistically 1–2 minutes of RTO. Active-active would demand conflict resolution on order state, and we declined that complexity. A real ceiling on the availability SLO — a conscious trade, not an oversight.

02
The payment provider's p99 is our p99

Authorisation can't be made async. Circuit breakers and a queued-capture fallback bound the damage, but a PSP degradation is visible to customers and no internal architecture fixes that.

03
At-least-once delivery everywhere

The outbox guarantees at least once, never exactly once, so every consumer must be idempotent. We enforce that with an idempotency-key table in DynamoDB — which becomes a hot partition during flash sales. The mechanism protecting correctness is itself a scaling constraint. Stated explicitly rather than discovered.

04
Inventory reservations live in Redis

Fast, and the reason the product page is quick. But a Redis failover with a cold replica opens a window where we can oversell. Mitigated with a TTL-based ledger in DynamoDB as the durable record; the window is narrowed, not closed. This is the decision I'd most want challenged.

05
Search is eventually consistent

Seconds behind the write path. “I just ordered it and it's not in my history” is expected behaviour — which makes it a support-training problem as much as an engineering one.

06
The EKS control plane is a shared failure domain

A bad admission webhook or CRD can wedge deploys cluster-wide. Separate clusters per domain would contain that at significant operational cost — currently judged not worth it, and worth revisiting as the team grows.

07
Cost

The two largest line items are NAT gateway egress and cross-AZ mesh traffic. We accept cross-AZ chatter because the alternative is AZ-pinned services and availability wins. NAT cost we attack with VPC endpoints — the same pattern as Part 1.

What running it actually caught

This module was written carefully and reviewed twice, including the adversarial pass in §1.3. Executing it still surfaced four defects that no amount of reading had found.

01
mock_provider mocks aws_iam_policy_document

It is nominally a data source, though it makes no API call — so the mock returned a random string for its rendered json, every IAM and KMS resource rejected it, and all twelve tests failed at plan time on an error unrelated to what was being tested.

02
instance_refresh.triggers was redundant

terraform validate pointed out that a launch template change always triggers a refresh. I had already trimmed desired_capacity from that list for being dead config — and left an entry that was dead for a different reason.

03
My terraform fmt checker had a bug

I had replicated fmt's alignment rule but missed one case: an attribute whose value opens a multi-line list (values = [) leaves the alignment group and takes a single space. My checker handled { but not [, so it actively mis-formatted two files.

04
ebs.encrypted is a string, not a boolean

The launch template schema types it as a string because the EC2 API does, so the planned value is "true" and "true" == true is false. The assertion failed against a volume that was correctly encrypted — a false alarm in a security guardrail, which is the kind that gets muted, after which the guardrail protects nothing. Fixed with tobool().

Three of those four are the same species as the interaction bugs in §1.3, and one is a bug in my own verification tooling. Which is the point: static review, human or AI, has a ceiling, and the only thing that reliably finds what sits under it is running the thing.
